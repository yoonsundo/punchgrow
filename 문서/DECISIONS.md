### 2026-08-11 — 물·불·바람·흙 원초 ORIGIN 4계보를 도감에 추가

**결정:** 기존 240종의 ID와 진화 연결은 그대로 보존하고, `PG-241..256`에 물·불·바람·흙을 상징하는 4개 독립 계보를 추가한다. 각 계보는 `PROCESS → AGENT → DAEMON → ORIGIN`의 4단계이며 시작형은 기존 시작 뽑기 풀에 합류한다. 최종형은 새 희귀도를 만들지 않고 ORIGIN을 유지하되 공통 금빛 마름모 원초 문장으로 구분한다. 전체 구성은 시작형 64 / 일반 진화 133 / 분기·혼합·특수 34 / 변이 25, 총 256종이다.

**왜:** 사용자가 최고 등급의 강함과 상징성이 부족하다고 판단해 단순한 강자 추가가 아니라 세계의 기반을 설명하는 4원소 존재를 요청했다. 별도 상위 등급을 만들면 기존 확률·천장·세이브 계약까지 흔들리므로 ORIGIN 안의 특별한 하위 정체성으로 두고, 유년기부터 최종형까지 성장 경험을 제공하기 위해 4단계 완성 계보로 추가했다.

**호환성:** 신규 ID는 기존 마지막 ID 뒤에만 붙이고 모든 진화는 직접 이전 단계 ID를 참조한다. 따라서 기존 도감 슬롯과 저장된 개체 ID의 의미는 바뀌지 않는다. 기존 `cute-redesign-v2` 240종은 기준 팩으로 보존하고 16종을 보강 자산으로 배포한다.

### 2026-07-31 — 사용량 수집 아키텍처 갭 발견 (미해결, 다음 논의 필요)

**발견 내용:** 최초 영감인 PokeTokenBar(https://chattymin.github.io/PokeTokenBar)는 코딩하는 컴퓨터 위에서 직접 도는 macOS 메뉴바 앱이라 로컬 CLI 로그를 바로 읽을 수 있다. PunchGrow는 모바일 앱이라 PC/맥의 코딩 도구 로그에 직접 접근할 수 없다.

**왜 중요한가:** 원래 스펙의 "사용량 수집은 로컬 저장 우선"이라는 전제가 성립하지 않는다. 데스크톱에서 도는 별도 수집기(실제 유닉스 데몬 프로세스) → 동기화 서버 → 모바일 앱(조회 + 배틀) 구조로 재설계가 필요해 보이나, 아직 확정된 결정은 아님. 다음 논의에서 최우선으로 다뤄야 함.

### 2026-07-31 — 핵심 동기: 개발량이 가챠 횟수와 희귀 확률을 높임

**결정:** Claude Code 토큰 사용량이 많을수록 가챠 기회뿐 아니라 희귀 크리처 등장 확률 자체도 높아진다. 확률 상승 상한은 존재하지만 헤비 사용자의 우위가 충분히 유지되도록 매우 높게 둔다.

**왜:** 사용자가 정의한 PunchGrow의 핵심 가치는 “개발을 많이 하면 좋은 가챠 결과를 뽑을 수 있어 토큰 사용하는 일이 즐거워지는 것”이다. 동일 확률의 뽑기 횟수만 늘리는 방식보다 실제 사용량에 따른 기대감을 강하게 만들기 위한 결정이다.

### 2026-07-31 — Claude Code 공식 OpenTelemetry 기반 PC/Mac 수집기 채택

**결정:** Claude Code의 공식 `claude_code.token.usage` OpenTelemetry 메트릭을 PC/Mac용 PunchGrow 수집기가 받아 동기화 서버로 보내고, 모바일 앱은 서버에서 결과를 조회한다.

**왜:** 모바일 앱은 사용자의 컴퓨터에 있는 Claude Code 사용량에 직접 접근할 수 없다. Claude Code는 공식적으로 거의 실시간 토큰 사용량 메트릭을 제공하므로 내부 JSONL 로그를 파싱할 필요가 없다. 프롬프트·코드·경로·명령어는 수집하지 않고 숫자형 사용량만 전송할 수 있다.

**보안 경계:** metrics-only 설정, 계정·이메일 식별자 로컬 제거, 암호화 전송, 명시적 동의, 연결 해제와 삭제 기능을 필수로 한다.

### 2026-07-31 — 결제 없는 단일 토큰 경제

**결정:** 별도의 코인이나 성장 에너지로 변환하지 않고 `토큰` 하나를 사용한다. 핵심 획득원은 Claude Code 실사용량이며, 출석·보상형 광고·운영 이벤트 지급을 무료 보조 획득원으로 허용한다. 현금 결제, 유료 가챠권, 유료 확률 혜택, 환급·판매·양도는 제공하지 않는다.

**왜:** 사용자는 Claude Code 사용량을 게임의 직접적인 활동 지표로 느끼기를 원하며 중간 재화가 불필요하다고 판단했다. 출석·광고·운영 보상은 결제 없이 재방문과 이벤트 운영을 돕는다.

**후속 확정:** Claude Code 실사용량, 출석, 보상형 광고, 운영 보상으로 얻은 토큰은 하나의 잔액으로 합산한다. 획득 내역에서 출처를 구분한다.

### 2026-08-05 — 주간 플랜 사용률은 공급자 원본 값만 표시

**결정:** Claude와 Codex의 주간 사용률을 토큰 합계나 임의 목표치로 환산하지 않는다. Claude는 로컬 OAuth 사용량 캐시의 `weeklyPercent`, Codex는 세션 로그의 주간 `rate_limits.primary.used_percent`를 읽는다. 값이 없으면 0%로 추정하지 않고 `확인 대기`로 표시한다.

### 2026-08-10 — 진화는 같은 종의 성장으로 읽혀야 한다

### 2026-08-10 — 진화 시각 검증은 실제 앱 번들 자산에 결합한다

**결정:** 진화 연속성의 최종 판정은 소스 폴더가 아니라 빌드된 `PunchGrow.app`의 리소스 번들을 기준으로 한다. 감사 manifest에 런타임 카탈로그와 240개 PNG의 SHA-256·바이트 수·가로·세로 크기를 기록하고, 119개 시각 검토 단위·190개 부모→자식 관계를 12개 컨택트 시트의 디코딩된 RGBA 픽셀 SHA-256·가로·세로·행 위치에 결합한다. 최종 원장은 모든 단위와 관계가 `PASS`·90점 이상·카테고리 일치일 때만 통과한다. 시트는 압축 PNG 바이트가 아니라 해상도와 RGBA 픽셀을 해시하므로 Node·zlib 버전이 달라도 같은 화면이면 같은 증거로 판정한다.

**실패 처리:** `WARN`과 `FAIL`은 독립 재심 기록 없이는 PASS로 바꿀 수 없다. 런타임 카탈로그·이미지·컨택트 시트가 감사 뒤 하나라도 달라지거나, 단위·관계가 누락·중복되거나, 혼합 진화의 두 번째 부모 증거가 빠지면 자동 검증을 실패시킨다. 사람이 수기로 적은 PASS나 이전 실행의 점수만으로는 통과할 수 없는 fail-closed 방식이다.

**왜:** 이전 검토는 소스 이미지와 컨택트 시트가 올바르다는 사실만 확인했기 때문에, 이미 빌드된 앱 번들에 오래된 리소스가 남아 있어도 PASS라고 기록할 수 있었다. 사용자가 실제로 보는 것은 `.app` 안의 자산이므로, 검토 결과를 그 정확한 바이트에 묶어야 소스와 실행 화면의 불일치를 검출할 수 있다.

**이번 기준선:** 런타임 PNG 240개, 시각 단위 119개, 부모→자식 관계 190개를 3개 독립 검토 묶음으로 전수 확인했다. 최초 판정은 PASS 108·WARN 9·FAIL 2였고, 비PASS 11개를 모두 재심했다. 9개는 부모 특징을 놓쳤거나 혼합체의 두 부모를 함께 보지 않은 오판으로 PASS 정정했다. 실제 실패인 `PG-216`과 `PG-237`만 다시 제작했으며, 최종 360px 런타임 판정은 각각 97점·96점, 전체 96점 PASS다. 최초 PASS 중 단위 또는 관계가 정확히 90점이었던 3개도 별도로 재심해 97~99점으로 다시 통과시켰다.

### 2026-08-11 — assignment-v3는 순환 없는 두 단계 결합으로 고정한다

**결정:** 교차 권한 supersession intent와 G003 delegation은 `continuity-assignment-v3.json`의 고정 경로, 스키마 원본 바이트 SHA-256, 결정론적으로 만든 envelope 제외 core SHA-256만 결합한다. 그 supersession의 출력이 확정된 뒤 assignment-v3 서명 봉투가 delegation 출력과 supersession 출력을 함께 결합한다. assignment core나 delegation에는 supersession 출력 해시를 넣지 않는다.

**왜:** supersession 출력이 assignment 출력에 의존하고 assignment 출력이 다시 supersession 출력에 의존하면 고정점을 가정해야 하는 순환이 생긴다. core를 먼저 결합하고 나중 봉투가 이미 확정된 supersession tip을 참조하면 같은 변조 방지 범위를 순환 없이 만들 수 있다. 검증은 봉투 네 필드를 제거한 core를 불변 G002-v2 assignment·topology에서 다시 만들고, 경로·스키마 원본 바이트·core·delegation·supersession 서명을 모두 일치시킨다.
